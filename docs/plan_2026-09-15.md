## Ordering constraints (why the blocks are sequential)

1. A construction run activates its own reserved split; nothing may read the pool while one runs, and
   pool_guard.assert_pool_of_record() will refuse. So the construction block runs only when the deployment
   queue and every analysis are idle, and ends with `pool_guard.py --activate` of the pool of record.
2. The deployment serves one judged queue at a time (8 workers). Runs are ordered cheap-and-load-bearing first,
   long last, so an instrument fault surfaces before the 18,000-call run starts.
3. Zero-call analyses are CPU-bound and read the pool by explicit id; they run in parallel with each other and
   with the judged queue, never with a construction.
4. Every judged script is built and dry-run at zero calls (payload assembled, counts printed, nothing posted)
   before it is queued; the first 12 matches of each run are a pilot read by the truncation guard.
