# Findings, 2026-07-31

Written at the end of a day of arena debugging and re-runs. Several of these contradict
what the thesis currently says, and two of them are load-bearing for claims that appear in
every chapter. Every number below was recomputed from the databases through one consistent
path — unpenalised Bradley–Terry MM fit, ground truth as each model's accuracy on exactly
the questions the arena judged, both tie conventions — and **does not match the values the
runs export themselves**, which apply a Jeffreys prior and a different ground-truth basis.
Do not mix the two sources.

Grid step at M = 12 is `6/(12³−12) = 0.0034965`. The decisive threshold is two steps,
`0.0069930`.

---

## 1. `sec:res-c5` does not isolate the partition

**This is the most consequential finding and it invalidates a claim made in eight files.**

`6_Results.tex:509–516` states that Run B "varies the partition itself: one arm judges each
question under its own leaf's rubric and rolls the per-leaf fits up by pooling sufficient
statistics; the other judges the same questions under a generic MT-Bench-style pairwise
prompt and fits Bradley–Terry directly at the domain … so the comparison is paired and
isolates the partition."

The distinction that claim rests on does not exist. Three separate checks:

**(a) Pooling per-cell statistics is arithmetically identical to ignoring cells.**
`TaxonomyRankingService.aggregateLeafScores` builds `pooledStatsMap` keyed on
`(modelA, modelB)` and sums wins, ties and comparisons into it. The cell identity is
discarded. Fitting the two ways on MAIN's identical verdicts:

```
identical ordering : True
max |theta| diff   : 0.000e+00
```

So "rolls the per-leaf fits up by pooling" and "fits Bradley–Terry directly at the domain"
are the same computation. The partition cannot reach the domain-level ranking through
aggregation at all.

**(b) C5 replays MAIN's triples, under MAIN's cells.** `TaxonomyBenchmarkService.kt:481–495`
loads `frozen_triples_<snapshot>_MAIN.json` and rebuilds each entry as a `BtMatchTask`
carrying MAIN's `nodeId`, `modelA`, `modelB`, `questionId`. Measured on the secured history
pair:

| | cells used | triples |
|---|---|---|
| MAIN | n00000104–107 (234/266/280/262) | 1042 |
| C5 | n00000104–107 (234/266/282/262) | 1044, **1042 shared with MAIN** |

So the scheduling channel is held constant too — C5's comparisons were *chosen by MAIN's
per-cell scheduler*.

**(c) The rubric is the only live difference, and that part the thesis has right.**
`TaxonomyArenaService.kt:500–540` has a dedicated `isC5` branch using
`GenericPairwiseJudgePrompt.SYSTEM_PROMPT` with `[[A]]`/`[[B]]`/`[[C]]` verbatim parsing —
genuinely the MT-Bench protocol. (`buildJudgeSystemPrompt`, whose `useGeneric` flag only
fires for `GENERIC_JUDGE`, is never reached on the C5 path.)

**Consequence.** Δρ between MAIN and C5 varies the *rubric* on a fixed partition, fixed
schedule and fixed aggregation. That is exactly what `sec:res-generic-judge` is described as
doing — and which the same paragraph correctly says "cannot test the partition, because both
of its arms replay the same leaf-scoped triples." The two sections test the same thing.

**Blast radius.** 23 references to `sec:res-c5` across `1_Introduction`, `4_Methodology`,
`5_Experimental_Design`, `6_Results`, `7_Discussion`, `8_Conclusion`, and appendices 10, 12,
7 and 8. The affected phrasing is of the form "the registered rule returned a verdict for
the partition-free arm".

**What Run B does measure**, and this is defensible: rubric specificity at matched budget on
a fixed partition. The pre-registration was written against a partition test, so it needs a
dated addendum recording the discrepancy rather than a quiet restatement.

**What a real partition test needs:** a third arm holding the rubric fixed and varying only
the grouping — comparisons scheduled over the whole domain with no cells, same judge prompt
as MAIN, same budget. That is a new scheduler condition, not a config change.

## 2. Per-cell profiles are unresolvable, and cell size is the reason

Applying the code's own local-resolution test (`n ≥ 5` and binomial `p × 11 < 0.05`) to each
cell's 11 rank-adjacent pairs, on history:

| run | adjacent pairs locally resolved |
|---|---|
| aggregate gate | **0 / 44** |
| per-cell gate (after the fix in §5) | **0 / 44** |

The fix in §5 raised adjacent-pair sample sizes from mostly `n = 1` to essentially all
`n = 12`, and *still* nothing resolved. So this is not a sampling artefact.

**It cannot be bought.** A `(cell, pair)` can only be judged on the distinct questions that
cell holds; re-judging the same question is not a new draw. History's cells hold 32–45
questions:

| cell | queries | σ now (n=12) | σ if every question used | 2.5σ | median adjacent gap |
|---|---|---|---|---|---|
| n00000104 | 32 | 0.263 | 0.161 | 0.403 | 0.268 |
| n00000105 | 41 | 0.246 | 0.133 | 0.332 | 0.156 |
| n00000106 | 40 | 0.268 | 0.147 | 0.368 | 0.264 |
| n00000107 | 45 | 0.260 | 0.134 | 0.336 | 0.290 |

**Even at total saturation, 2.5σ stays above the median adjacent gap in every cell.** The
bound is optimistic: it assumes independent draws and ignores that a ~24% tie rate cuts
effective information further.

Cost to force resolution anyway: ~22,400 leaf-credited comparisons even capping the
impossible pairs at 2,000 each (uncapped it exceeds a million — 7 of 44 adjacent pairs have
gaps of 0.003–0.033, one needing 658,000). That is ~17× the current run, for the smallest
domain in the batch.

**Physics is not the larger-cell test it looks like:** 237 routed questions over 10 cells is
~24 per cell, *worse* than history's ~33.

**Recommended framing.** Report the per-cell profile at the resolution it supports — a
coarse capability gradient (θ spread is 9–13 SE) but not an ordering (adjacent gaps ≈ 1 SE) —
and report the cell-size ceiling as a measured structural limit rather than a budget
shortfall. There is a granularity/resolution tradeoff here with numbers attached, and it
explains the RQ2 null mechanically instead of leaving it a bare negative.

## 3. Withholding the multiple-choice options

The judge **is** shown the option block on every arena run to date:
`TaxonomyArenaService.kt:674` builds `"$query\n\nOptions:\nA) …"` and passes it as the
`query` argument. (The correct option is never passed — answer-key blindness is intact. The
options are the candidate set, not the key.) A `judgeSeesOptions` flag now controls this and
applies to both arms, since it is read before the condition branch.

| arm | ρ half-weighted | ρ ties-dropped |
|---|---|---|
| MAIN option-visible | 0.846154 | 0.846154 |
| MAIN option-blind | **0.811189** | **0.804196** |
| C5 option-visible | 0.846154 | 0.853147 |
| C5 option-blind | 0.846154 | 0.846154 |

`0.846154` is where every configuration lands **except** option-blind MAIN — across four
configurations and ~4,000 verdicts. Two further MAIN option-visible runs differing by 20% in
budget and in routing semantics also both give exactly 0.846154.

**Not established:** that the ρ drop exceeds run-to-run variance. There is no designed
same-configuration replicate. One repeat of MAIN option-visible at a different seed would
settle it cheaply.

### CORRECTION (same day, later): the option-blind effect was largely an artefact

The blind condition withheld the candidate set AND left the answer letters bare, and those
are two different manipulations. Measured over 2,000 reserved traces: **72% end in "the
answer is (X)" and only 23% carry the option's text anywhere nearby**, so under BLIND roughly
half the traces' conclusions are unreadable — "(C)" against "(F)" with no referent. A fall in
agreement there cannot be split into "assessed the reasoning instead" and "could not tell
what was claimed".

A third mode, RESOLVED, separates them: no candidate set, but each trace carries its OWN
selected option resolved from `pred` to the option text (attached to 2,018 of 2,028 traces,
99.5%; `gt_answer` never consulted, so key-blindness is intact). That holds "can the judge
tell what each model concluded" fixed and varies only "can the judge use the candidate set".

| MAIN arm | verdicts | tie rate |
|---|---|---|
| OPTIONS (candidate set shown) | 1,042 | 22.7% |
| **RESOLVED (own answer resolved)** | 1,014 | **24.4%** |
| BLIND (bare letters) | 968 | 32.2% |

- RESOLVED vs OPTIONS: **+1.7pp, ≈0.9 SE** — no detectable difference
- RESOLVED vs BLIND: **−7.8pp, ≈3.9 SE** — clearly different

**So withholding the candidate set costs the judge essentially nothing in decisiveness,
provided it can read what each model answered.** The 23.3% → 29.7% shift reported above is
mostly unreadable letters, not loss of an answer-checking shortcut.

This does NOT support "the judge reaches its verdict via the option list". It supports
something narrower: the judge needs to know what each model concluded, which is not the same
as needing the candidate set to check it against. The OPTIONS-vs-RESOLVED contrast is the
RQ1 test; the OPTIONS-vs-BLIND contrast conflates two manipulations and should not be
reported as a mechanism result.

**Mechanism.** A hypothesis that the per-cell rubrics under-emphasise correctness was
**refuted**: all 87 mention correctness terms (`correct` in 87/87, `valid` 82, `accura` 51),
against `correct` alone in the generic prompt. Reading the text, the per-cell rubrics direct
the judge at *process* — "verify closure, associativity, identity, and inverses", "are the
preconditions of all formulas explicitly validated" — while the generic one says only "grade
them based on overall correctness and reasoning quality". So the rubric works as designed and
makes the judge assess reasoning; the ground truth is answer accuracy, so **a judge that
evaluates reasoning is being scored against a different target**.

## 4. Spearman ρ on 12 models is too coarse for these contrasts

The grid quantum is 0.0034965 and the decisive threshold is two of them. Consequences:

- **Identical ρ does not mean identical ranking.** All four history arms land on values that
  coincide while their orderings differ by 1–3 positions.
- **The 2-step boundary is a seam.** Two grid steps is 0.0069930, seven millionths *below*
  the 0.007 the pre-registration quotes, and results land on it exactly (history ties-dropped
  Δρ = −0.006993; the mathematics run hit the same seam with the opposite sign). Decisive
  under the rule's stated meaning, not under its literal number. **This needs one ruling
  applied to every domain**, not a per-run decision.
- Per-verdict metrics with n in the thousands (tie rate, judge/key agreement) carry far more
  power than a 12-model rank correlation and should carry the argument where available.

## 5. Bugs found and fixed today

| bug | effect | fix |
|---|---|---|
| Confidence gate computed on the **aggregate** board, keyed on the pair alone | A pair settled domain-wide was suppressed **in every cell**, retiring exactly the comparisons that could show a cell ordering differing from the pooled one. 45/66 suppressed after round 1, 57/66 by round 4. | Keyed per cell (`nodeId\|modelA\|modelB`), tested against that cell's own θ/SE |
| `isLeafConverged` counted a gate-suppressed pair as terminal | Cells were declared converged on evidence gathered elsewhere. Three of four "converged" with **0/44** adjacent pairs locally resolved — the run stopped for want of schedulable work and recorded it as convergence | Gate is now local, so the terminal condition is local evidence |
| `inconsistentLeafIds` used `.any {}` over 66 pairs | One weak pair discarded a whole cell. From round 2 **every** cell was discarded → pooled fit on zero comparisons returning twelve zeros, all SEs falling back to 1.0, and `[ARENA-GAUGE]` silenced exactly when it would have caught this | Pooled leaf-level agreement with a minimum sample |
| `judgeAgreed` counted matches where the key abstains | Agreement scored against a reference that says TIE whenever both models are right or both wrong; rate pinned near 0.45 regardless of judge quality | Only decidable matches counted; rate moved to 0.561–0.650 |
| Cached verdicts re-propagated into pair statistics | One judgement counted several times; 12% phantom evidence on the 2026-07-31 history run (1339 leaf-credited vs 1182 verdicts) | Skipped on cache hit, with a `replayed` counter |
| Arm budgets matched on **leaf-credited** comparisons | Under multi-membership only MAIN can inflate; C5 would have received 1,309 real judge calls against MAIN's 1,098 — 19% more evidence for the arm the contrast is measured against | Matched on verdicts; multi-membership then removed entirely, so the counts coincide |
| `judgeSeesOptions` absent from `parseToml`'s key whitelist | Config said `false`, run judged **with** options, dump showed `null`. Silent | Wired at all three points |
| `targetRps` injected and never read | `-Darc.ollama.target-rps` inert; every run paced at the hardcoded 5.0 | Field reads the injected value; `[ARENA-PACING]` logs it at startup |

**Note the shape of the last two.** `parseToml` dispatches on an explicit key whitelist, so
**any TOML key not in it is silently ignored**. If a config value has ever appeared to have
no effect, that is the first thing to check.

## 6. The arena is rate-bound, not permit-bound

New `[ARENA-LAT]` instrumentation separates the three things a call can block on. Physics,
32 permits, `target-rps = 4.0`:

```
calls=1400 retries=0 | per call: rate=30839ms (63%) permit=8275ms (17%) http=10225ms (21%)
                     | http p50=8816ms p95=20198ms p99=28762ms | inflight max=32/32
                     | BOTTLENECK=rate
```

Two thirds of every call's life is queued at the pacer: a round dispatches all 264 requests
at once and they drain at 4/s, so the last waits over a minute.

**This corrected an earlier wrong diagnosis.** From round durations and permit counts via
Little's Law the system looked permit-bound; `target-rps` was raised 3 → 4 (inert, the pacer
sat at 60% utilisation) and `max-parallel` was cut 32 → 24 (a real ~25% throughput loss).
The http latency estimate was roughly right (8.0s measured vs ~10s inferred); the
*attribution* was wrong.

Also measured: **each match costs two Azure calls** (both presentation orders, issued
concurrently), so request rate is twice match rate — easy to under-count. Reserved-pool
traces are short (median 792 chars), so a judge prompt is only ~700–860 tokens; at 4.0 req/s
that is ~240 RPM and ~200–242k TPM, under half the 500 RPM / 500k TPM ceiling. The
790-429 episode was 32 permits at rate 5.0 — **the rate caused it, not the permit count**, so
lower `target-rps` first if throttling reappears.

A growing tail is visible: p50 flat (8.0 → 8.8s) while p95 climbs 14.9 → 20.2s and the permit
share doubles 9% → 17%. If that continues, permits will eventually bind and the bottleneck
will flip.

## 7. Claims I made today that turned out to be wrong

Recorded because each was stated confidently before being checked, and anything downstream
of them should be re-verified.

| claim | reality | how it went wrong |
|---|---|---|
| "The judge is not shown the options" — edited into three chapters | It is, on every run | Sampled `match_history.query`, which stores the cache key, not the judge prompt |
| "First run that stopped by convergence rather than exhaustion" | Same exhaustion, relabelled — convergence was supplied entirely by gate suppression | Read the convergence counter instead of testing whether any pair resolved locally |
| "C5 is not a generic judge" | It is — dedicated `isC5` branch uses the MT-Bench prompt | Read `buildJudgeSystemPrompt` and generalised without checking it was on the C5 path |
| "77% agreement proves same judge run twice" | Two different judges also agree often when the quality gap is obvious | Inference didn't discriminate between the hypotheses |
| "C5 replays at double the rate" | 17% faster (1.59 vs 1.36 matches/s) | Repeated an integer-rounded log field as a measurement |
| "Permit-bound, restore max-parallel to 32" | Rate-bound; 65% of wait is the pacer | Little's Law inference with the wrong assumption about which resource was saturated |

The recurring pattern: reading one code path or one log field and generalising without
checking it was the path actually taken.
