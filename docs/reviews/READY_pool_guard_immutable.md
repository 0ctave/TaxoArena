## Defects

**D1 (HIGH): `-journal` not refused; immutable reads uncommitted pages from a rollback-mode DB.** Shown by execution in claim 2. No registered pool DB is rollback-mode today: p2dca, paeec, 20NG and snapshots.db all have header bytes 18/19 = 2/2, read from the raw header without sqlite. But `--db` accepts any DB, and the BFCL and MULTISWE DBs are rollback-mode (1/1) and are the objects POOL-REGISTRY-BFCL will register. The old code failed loudly on the same input. Fix: in `open_ro`, after the -wal check and before the connect, raise `[POOL-GUARD]` when `<abs>-journal` exists with size > 0. A scratch copy (`fix/`) refuses `hot.db` and still passes 15/15 under python and -O. An alternative, stronger fix: use `immutable=1` only when header byte 18 == 2 (WAL), and keep plain `mode=ro` for rollback-mode DBs. That form creates no sidecar there (claim 1d) and keeps locking and hot-journal detection. Add selftest cases: a hot journal is refused before any connect, and a live rollback writer is refused.

**D2 (MEDIUM): the selftest does not model the real sidecar state, so mutant M3 survives.** Add three cases: (i) 0 B -wal beside a 32 KB -shm, the state of p2dca and paeec: accepted, and the -shm size, mtime and sha unchanged; (ii) non-empty -wal with no -shm: refused before any connect; (iii) a check that the refusal is substantive: on the case-3 DB, the `immutable=1` view and the `mode=ro` view differ (row count), so the -wal rule is shown to guard a real divergence.

**D3 (MEDIUM, operational, for the author): the -wal refusal meets the 20NG line and every killed JVM.** The 20NG DB's -wal (708672 B, mtime 2026-09-23 04:30:05.638) postdates its main file (2026-09-22 19:32:36.251). The old guard's 04:35:06 output `pool_guard_ng_af_bareq512_s42.out` prints `reserved_pool_meta ... created_at=1790130605620` (04:30:05.620). The latest meta row is therefore consistent with living only in that WAL tail: the refusal guards a real divergence, not a formality. This is inferred from mtimes and the recorded output; the DB was not opened, as instructed. Consequences: (a) `tools/chains/topic_partition.sh` `pool_export` (L533-L537) logs any non-zero guard exit as **"C0 pool clause FAILED"**. That is a registered outcome, not a failed precondition, so a post-build WAL tail would be recorded as a FAILED criterion. The two existing arms short-circuit on their ` OK:` .out files, so a resume is affected only for a NEW arm (T2) or a deleted .out. (b) Any `assert_pool_of_record(pf844849e133cda4e, db=20NG)` refuses until the WAL is checkpointed. (c) After a killed or OOM JVM (the 05:00 site-null OOM left this one), there is no "writer" to close. The refusal text's remedy ("close the DB's writer (which checkpoints it)") is then incomplete: the remedy is a backed-up read-write open and close by the data-steward, outside any rule-7 window. Fix: the refusal message names both remedies; topic_partition.sh maps the `[POOL-GUARD] ... -wal is non-empty` refusal to "precondition failed / UNDETERMINED", never to C0 FAILED; checkpoint the 20NG WAL (after a backup) before TOPIC-PARTITION-20NG resumes through the new guard.

**D4 (MEDIUM, residual, documented only): `immutable=1` removes SQLite's locking.** The -wal check and the connect are not atomic. A WAL writer that checkpoints, or a rollback writer that starts, during the read gives a torn read without error, where `mode=ro` would have blocked or errored. The mitigation is rule 7 (W1-W5 exclusive-open probe, no writer while a pool reader runs). State this in the docstring bracket beside the -wal rule.

**D5 (LOW): the docstring says "Every DB is opened read-only", and open_ro's comment names only the -wal hazard.** After the fix, name -journal too.

**D6 (LOW, informational): a selftest that crashes on an uncaught exception leaves `%TEMP%\pool_guard_selftest_*` behind.** Two such directories (8 KB each) came from my crashing mutants M6 and M8 and were removed. The passing path cleans up.
